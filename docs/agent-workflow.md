# Agent 协作开发流程

## 目的

本规范用于指导多个 Agent 协作开发 Cqlib 框架下的算法库和算子库。流程以组件化、标准化、可组合、可验证和易扩展为原则，同时为 Agent 保留充分的技术判断空间，避免用过细的操作步骤限制实现方案。

每个开发任务依次经过方案设计、代码开发和独立审计三个角色。主协调 Agent 负责分配任务、控制并行范围和传递产物，不代替三个角色完成其核心职责。三个角色应依据已经确定的协议、接口和仓库规范自主作出技术决策，日常开发不要求人工逐项复核。

本工作流止于形成经过完整预提交验证的本地交付物。Agent 不负责向远端推送代码，也不创建、审批或合并 PR；通过审计的代码和报告交由开发人员或仓库维护者处理后续 Gitee 流程。

## 协作流程

```text
任务与设计思路
    ↓
方案设计 Agent
    ↓
代码开发 Agent
    ↓
审计评估 Agent
    ↓
功能完备性验证
    ↓
基于目标主分支最新代码的本地候选合并验证
    ↓
通过：输出可提交代码和预提交审计结论
    ↓
开发人员或仓库维护者处理 PR

未通过：返回方案设计或代码开发阶段
```

同一任务中的三个角色按顺序协作。不同且相互独立的算法或算子可以在不同分支和工作区中并行开发。PR 提交后的审批、CI 和合并不属于三个 Agent 的职责范围。

## 方案设计 Agent

方案设计 Agent 负责完整理解任务、用户设计思路、仓库规范、现有实现和真实 Cqlib 接口，并将其整理为可实现、可验证的技术方案。

其主要任务是：

- 明确目标、范围、非目标、依赖和未决问题；
- 对具体算法调研一至两篇权威且讲解充分的论文，优先选择原始论文，并按需要补充分析、改进或实现类论文；
- 给出算法或算子的数学定义、接口语义和模块边界；
- 说明端序、相位、归一化、测量和数值容差等关键约定；
- 设计与现有 Cqlib 能力兼容的实现方式，不臆造 API；
- 提出测试思路、独立参考方法和客观验收标准；
- 识别与其他并行任务的依赖或冲突。

算法方案应记录论文来源和所采用的算法版本，并从论文的数学定义、前置条件、输入输出、复杂度和误差约定中推导接口、参数、函数类型、边界行为与验收要求。论文提供理论依据，最终接口仍须符合项目既定协议和 Cqlib 的真实能力。

对于缺少适用论文的算子或基础组件，必要时可参考公开标准、成熟开源项目的官方文档和测试来比较接口组织、参数语义与边界设计。方案应记录参考来源、版本和具体接口，并根据 Cqlib 的类型体系与架构独立设计；不得直接复制实现、臆定不同项目的语义等价或因此引入不必要的运行时依赖。

方案设计 Agent 原则上不直接编写生产代码。遇到一般技术歧义时，应结合现有协议、接口、仓库实现和验收目标直接作出有依据的决策；只有在规则相互冲突、必要信息缺失，或涉及公共接口破坏、安全、许可证、仓库权限等超出既定授权范围的问题时，才交由主协调 Agent 或相应负责人决定。

## 代码开发 Agent

代码开发 Agent 负责根据已确认的方案完成代码、测试和必要文档，并确保实现符合仓库规范和验收目标。

其主要任务是：

- 在指定任务范围内实现算法或算子，不擅自扩大需求；
- 优先复用 Cqlib Core 已有的线路、门、算子、量子信息、编译、结果和执行能力，保持算法与具体平台和后端解耦，避免在算法库中重复实现 Core 应承担的功能；
- 编写清晰、可组合、带类型标注的公共接口；
- 同步完成单元测试、边界测试、使用示例及必要的解析、经典参考或性质验证；
- 记录与设计方案的实质偏差，并在继续前报告接口、依赖或范围问题；
- 如实报告实际执行的检查、结果和环境限制。

代码开发 Agent 不应通过增加无需求的抽象、放宽数值容差或绕过正常包安装来使实现或测试表面通过。

发现 Cqlib Core 缺少必要能力或现有能力疑似异常时，代码开发 Agent 不应静默复制实现或猜测替代接口。应先通过最小复现和针对性测试排除误用、环境或版本问题；确认后，在任务交付目录而非源码目录中输出独立的 `core-gap-report.md`。报告只需清晰说明 Core 版本或提交、涉及接口、期望与实际行为、复现证据、任务影响和需要补充的能力。未经确认，不把 Core 修改或临时规避方案混入算法代码；若缺口阻止正确实现，应将任务标记为阻塞。

## 审计评估 Agent

审计评估 Agent 负责 PR 提交前的独立代码审计和完整功能验证，判断实现是否满足原始任务、设计方案、Cqlib 语义、代码规范和验收标准。审计不能只依赖开发 Agent 的总结，应检查实际代码差异并亲自执行适用的测试与示例。

其主要任务是：

- 检查需求覆盖、架构合理性和公共接口质量；
- 核对算法论文或算子参考资料是否可追溯，并确认关键接口决策与所采用的数学定义、Cqlib 规范一致；
- 验证数学定义、端序、相位、容差和边界行为；
- 核对实现使用的 Cqlib 接口是否真实且语义兼容；
- 执行与变更相关的测试、完整 pytest 测试集、使用示例和文档示例，并按仓库配置执行必要的静态检查或构建验证；
- 评估测试是否具有独立性，能否发现合理的错误实现，而不是仅确认开发 Agent 编写的测试能够通过；
- 检查公共功能、边界场景、异常行为和必要示例是否齐全，确认任务不是只有局部测试通过而功能仍不完整；
- 在隔离的本地候选合并状态中，将代码与目标主分支的最新可用代码组合并执行必要回归测试，确认预期合入后不会产生接口、依赖或测试冲突；
- 审核 Core 缺口报告及其复现证据，确认问题确属 Core 能力缺失或异常；
- 检查循环依赖、无必要依赖、越界修改和并行任务冲突；
- 记录实际执行的命令、结果、目标主分支基准提交和无法执行的检查，并给出通过、需要代码返工、需要方案复审或因条件不足而阻塞的明确结论。

审计评估 Agent 默认不直接修复被审计代码。实现问题返回代码开发 Agent，方案问题返回方案设计 Agent；只有新的代码和证据能够关闭审计问题。

审计结论必须分别回答两个问题：功能和交付物是否完整；代码基于记录的目标主分支基准是否具备安全集成条件。两项均通过后，结果才可标记为“可提交”。该结论只覆盖提交 PR 前的技术状态，不代表 Agent 已经推送代码、创建 PR 或完成真实主分支合并。

## 公共开发规则

- 开始工作前阅读仓库最新的 `AGENTS.md`、`README.md`、`docs/development.md` 和 `pyproject.toml`，以仓库当前规则为准。
- 基础和可复用组件放在 `src/cqlib_algorithms/` 的适当功能模块中，完整算法放在 `src/cqlib_algorithms/algorithms/`；只为真实实现增加模块，不预建空分类或推测性的 `components`、`contracts` 层。
- 复用 Cqlib 的真实类型和语义。本库不负责平台登录、凭据管理、厂商适配和通用任务提交基础设施。
- 保持依赖无环；新增公共抽象或第三方依赖必须有当前需求支撑。
- 支持 Python 3.10 及以上。代码、标识符、注释、文档字符串和异常信息使用英文；README 保持中文。
- 公共接口使用类型标注，并说明输入、输出、边界条件、异常和关键量子语义。
- 测试放在 `tests/`，不通过修改 `sys.path` 绕过包安装。代码、必要测试和使用说明同步更新。
- 算法正确性应使用解析结果、独立经典参考、性质测试、精确仿真或合理的跨框架对比验证，不能仅用共享同一实现逻辑的代码相互证明。
- 未发布的 Cqlib SDK 由开发者按批准来源手动安装。现阶段不执行 `uv sync`；相关验证使用 `uv run --no-sync pytest`，打包相关修改使用 `uv run --no-sync python -m build`。
- 版本维护在 `pyproject.toml`，保留 `LICENSE.txt` 和项目既定许可证信息。
- 运行过程中的临时提示、推理记录、凭据和本地工作资料不纳入拟提交变更；交付物只包含任务所需的代码、测试、示例和正式文档，且不得泄露内部代码或敏感信息。

## 并行开发规则

- 每个并行任务使用独立功能分支，Agent 只修改分配给自己的任务范围。多人可以分别使用独立 clone；同一台机器或同一自动化环境并行处理多个任务时，应使用相互隔离的工作目录，可选择 Git Worktree、独立 clone 或其他等效方式。
- 只有在实现文件、测试文件、公共接口和依赖关系相互独立时才并行；存在前置依赖时改为顺序开发。
- `__init__.py`、`pyproject.toml`、公共类型、共享测试工具和全局文档等共享内容应指定单一负责人或留到集成阶段统一处理。
- 各线路都必须结合目标主分支最新可用代码验证本地候选合并状态，确认独立实现不会在集成时产生冲突。预提交审计应记录所用基准提交；若正式提交前目标分支已经变化，原审计结论不再覆盖新状态，应重新执行必要验证。
- 原则上一个独立任务对应一个分支，并形成适合单独提交的交付物，便于后续审查、回退和追踪。开发人员可以根据仓库权限从个人 Fork 分支或源仓库内功能分支创建 PR，但 Agent 不直接执行该操作，也不直接在主分支或受保护分支上开发。

## 完成标准

只有当功能和交付物完整、相关测试与独立正确性验证通过、适用示例能够运行，并且基于已记录的目标主分支基准完成本地候选合并与回归验证后，审计评估 Agent 才能给出“可提交”结论。交付内容包括代码、测试、必要示例和正式文档；存在 Core 缺口时还应包含独立的缺口报告。无法验证的接口、未执行的检查和已知限制必须明确报告，不能作为已经完成处理。Agent 在输出交付物和预提交审计结论后结束本流程，后续推送、PR、CI、审批和合并由开发人员或仓库维护者负责。
